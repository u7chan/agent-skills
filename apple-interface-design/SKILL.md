# Apple Interface Design

Appleの見た目を模倣するのではなく、入力への即応、物理的な連続性、空間的一貫性、抑制、アクセシビリティをWebへ翻案する。

## 必須原則

- 入力開始時から反応し、操作中も1対1で連続的にフィードバックする。
- モーションを現在の表示値から始め、リリース速度を引き継ぎ、途中で掴み直して反転できるようにする。
- リリース位置だけでなく、速度から投影した到達位置を使ってスナップ先を決める。
- 表示と非表示の経路、操作の起点、奥行きの変化を空間的に一致させる。
- バウンドを装飾として使わず、ジェスチャーに慣性がある場合だけ弱く使う。
- モーション、透明度、コントラストの軽減設定に、情報を失わない代替表現を用意する。
- 数値を固定の正解とみなさず、実機の入力、表示密度、コンテンツ、フレーム時間で調整する。

## ワークフロー

1. 対象の目的、主要タスク、入力方式、既存デザインシステム、対応ブラウザ、性能制約を確認する。
2. 状態、スナップ点、操作開始・更新・終了・キャンセル、割り込み、復帰経路を先に定義する。
3. 下のルーティングに従い、該当する参照資料を読む。レビューでは `references/review-checklist.md` も必ず読む。
4. 操作とビジュアルを同時に設計し、可能なら触れるプロトタイプを作る。
5. 通常速度、低速再生、途中の掴み直し、反転、境界超過、異なる入力方式で検証する。
6. reduced motion / transparency / contrast、キーボード操作、拡大文字でも同じ目的を達成できるか確認する。

## 実装上の判断

- Pointer Eventsとpointer captureを基本とし、掴んだ位置のオフセットを維持する。
- ジェスチャー中は状態を毎フレーム反映し、完了後だけアニメーションする実装を避ける。
- 直接触れる要素では、固定時間のキーフレームより、現在値と速度を保持してターゲット変更できるスプリングを優先する。
- アニメーション対象を主に `transform` と `opacity` に限定し、レイアウト計算とpaintを監視する。
- Motion / Framer Motionなどを使う場合は、現行APIの速度単位とspring optionを確認する。Appleのdamping ratio / responseと同名であっても意味が同じとは仮定しない。速度を引き継ぐ操作に、速度を無視するduration-based springを使わない。
- Webの対応状況が揃わないメディア特性には、CSSの通常値を安全なフォールバックとして置く。

## レビュー出力

- 問題を「違反している原則 → ユーザーへの影響 → 最小の修正案」の順で示す。
- 重大度は、操作不能・前庭刺激・予測不能・入力遅延・視覚的な粗さの順に判断する。
- 単に「Appleらしくない」と評価せず、観察可能な挙動と検証方法を示す。
- 良い点も、どの原則を満たすかを短く示す。
