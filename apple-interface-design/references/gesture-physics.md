## 1. 速度サンプリング

リリース直前の短い位置履歴から速度を求める。

- `pointermove`ごとに位置と`timeStamp`を記録する。
- 古すぎるサンプルを捨て、停止直後の過去速度を残さない。
- 1イベントだけの差分はノイズを受けやすいため、直近数サンプルまたは短い時間窓を使う。
- `getCoalescedEvents()`を利用できる場合は、高頻度入力の精度向上に使える。対応は限定的なので通常の`pointermove`へフォールバックする。
- ライブラリへ渡す前に、単位がpx/msかpx/sかを確認する。

速度はドラッグからアニメーションへの継ぎ目を消すために使う。位置だけを合わせても、速度が不連続なら滑らかには見えない。

## 2. 慣性の投影

離した位置に最も近い点へ即座に丸めず、速度から停止位置を予測する。

```js
// initialVelocity: px/s
function project(initialVelocity, decelerationRate = 0.998) {
  return (
    (initialVelocity / 1000) *
    decelerationRate /
    (1 - decelerationRate)
  );
}

const projectedEndpoint = currentPosition + project(releaseVelocity);
const target = nearestSnapPoint(projectedEndpoint);

animateSpringTo(target, { velocity: releaseVelocity });
```

- 通常のスクロール感の出発点には`0.998`、短く機敏な投影には`0.99`程度を試す。
- この値はフレームレート、座標単位、対象サイズ、入力デバイスに合わせて検証する。
- 物理学の一定減速度モデル`v² / (2 × decel)`へ無条件に置き換えない。ここでは指数減衰モデルを使う。
- 投影結果は許容範囲へ制約し、その後スナップ候補を選ぶ。

## 3. スナップ先の決定

スナップ先は次の順で決める。

1. 現在位置、リリース速度、投影位置を求める。
2. ジェスチャーが確定条件を満たすか判定する。
3. 投影位置に最も近い有効なスナップ点を選ぶ。
4. 現在速度を維持したスプリングで移動する。

戻すか確定するかの二択では、位置だけでなく速度の符号と大きさを使う。高速で明確に閉じる方向へ動いているなら、位置が中間点を越えていなくても閉じる判断が自然な場合がある。

誤操作を防ぐ必要がある破壊的操作では、速度だけで確定せず、距離・明示的確認・取り消し可能性を組み合わせる。

## 4. ラバーバンド

境界で急停止させず、超過量が増えるほど追従量を減らす。

```js
function rubberband(overshoot, dimension, constant = 0.55) {
  return (
    overshoot *
    dimension *
    constant /
    (dimension + constant * Math.abs(overshoot))
  );
}
```

- `overshoot`は境界を超えた距離、`dimension`は対象となる表示領域の寸法とする。
- 境界内では1対1、境界外でだけ抵抗を適用する。
- リリース後は速度を引き継いで有効範囲へ戻す。
- 視覚だけでなく値の制約も別に保持し、保存データへ超過値を流さない。

## 5. ジェスチャー認識

### タップ

- 押した瞬間にハイライトし、離したときに確定する。
- 対象周辺に約10pxを出発点とするヒステリシスまたは余裕を持たせる。
- 対象外へ出たら一時キャンセルし、離す前に戻ったら再び有効にする。
- キーボードのEnter / Spaceにも同じ意味のフィードバックを用意する。

### ドラッグとスワイプ

- 約10pxを出発点とする小さな移動しきい値の後に方向を確定する。
- 方向確定後は1対1で追従する。
- 最初の移動から候補ジェスチャーを並行評価し、意図が明確になったら競合候補を確実にキャンセルする。
- `swipeleft`のような終了結果だけの認識へ依存せず、途中の移動量を使って連続フィードバックする。
- ダブルタップ判定はシングルタップを遅らせるため、本当に必要な場所だけで使う。

しきい値はCSS pixel、入力方式、対象サイズ、運動障害への配慮を踏まえて調整する。10pxを普遍的な正解にしない。

## 6. フレーム品質

滑らかさは平均FPSだけでなく、各フレームの移動量と時間の安定性で評価する。

- `requestAnimationFrame`を表示同期クロックとして使う。
- 位置更新は主に`transform`、可視性は主に`opacity`で表現する。
- layout、paint、compositeのコストを開発者ツールで確認する。
- `will-change`はモーション直前に限定して付け、常時大量に指定しない。
- 高速移動でストロボ感が出る場合だけ、弱いブラーや伸びを検討する。
- 60Hzだけでなく高リフレッシュレートでも時間ベースで動くか確認する。
- 長いtask、GC、画像decode、同期レイアウトが入力経路へ入っていないか調べる。

高速表現のブラーは可読性とreduced motionを損なう可能性がある。装飾ではなく、軌道の理解を助ける場合だけ使う。
