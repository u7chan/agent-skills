# 出力フォーマット

QA観点出しの結果は、次の章立てを保って出力する。
読み手が「どの技法でどこまで見たか」を確認できる形にする。

```markdown
## 対象
（テスト対象の1〜2行説明：仕様／関数名／画面名／PR番号など）

## 前提・スコープ外
- 前提として置いた仕様の解釈（曖昧な点があれば明示）
- 今回スコープ外とした観点（理由つき）

## 1. 同値分割
| グループ | 代表値 | 期待結果 |
|---|---|---|
| ... | ... | ... |

## 2. 境界値分析
| 値 | 位置 | 期待結果 |
|---|---|---|
| 0 | 下限の直前 | 無効 |
| 1 | 下限 | 有効 |
| ... | ... | ... |

## 3. デシジョンテーブル
（条件の組み合わせ表。該当しない場合は「該当なし: 単一条件のため」と1行で書く）

## 4. 状態遷移
（状態がない対象なら「該当なし: 状態を持たないため」と1行で書く）

## 5. エラー推測（危険パターン）
- [ ] 二重送信: 送信ボタン連打で副作用が1回だけになること
- [ ] タイムゾーン差分: JST/UTC境界で日付がずれないこと

## 6. チェックリスト照合
| 出典 | 項目 | 対象に当てはめた具体ケース |
|---|---|---|
| checklist-api.md / 入力検証 | 必須パラメータ欠損で400 | `{}` を送って400が返ること |
| checklist-ui.md / 操作・送信 | 二重送信できないか | 送信ボタン連打でAPIが1回だけ呼ばれる |

## まとめ：実装すべきテストケース一覧
| # | 観点 | 入力 | 期待結果 | 由来した技法 |
|---|---|---|---|---|
| 1 | ... | ... | ... | 境界値 |
```

## 曖昧さの書き方

- 致命的な曖昧さ: 観点出し前に確認質問を出す。
- 仮置きする曖昧さ: `（仮置き）成功時は200を返す前提` のように書く。
- スコープ外: `今回は認可済みユーザーの挙動のみ対象` のように理由を添える。
