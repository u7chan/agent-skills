# QA Test Design

テストコードを書く前に、仕様・コード・PR・画面・APIからQA観点と実装すべきテストケースを洗い出す。
正常系だけに偏らず、境界・異常系・組み合わせ・状態遷移・事故パターンを人間がレビューしやすい形に整理する。

## ワークフロー

1. **対象を特定する**
   - 仕様書、関数、画面、API、PR差分など、何をテスト設計するのかを明確にする。
   - ローカルコードやPR差分から分かることは先に確認する。

2. **曖昧さを扱う**
   - 観点の軸そのものを決められない曖昧さは、観点出しを止めてユーザーに確認する。例: 対象機能が不明、正常終了条件が不明、成功/失敗で守るべき業務ルールが不明。
   - 一部の期待結果だけが未確定な曖昧さは、「確認が必要」として前提・スコープ外に明記し、観点出しは進める。例: パスワード最小/最大長、ロックアウト回数、配送可能日時、クーポン無効時に注文を止めるか。
   - 一般的な慣習で置き換え可能な曖昧さは、「仮置き」として前提・スコープ外に明記して進める。例: 入力不正は400、送信中はボタン無効化、認証失敗は共通エラー表示。
   - 今回の観点に効かない曖昧さは、理由を添えてスコープ外として扱う。
   - 未確定仕様に依存するテストケースでも期待結果欄を空にしない。`確認待ち: <確定が必要な仕様>` または `（仮置き）<期待結果>` の形で、何が未確定かを読めるように書く。

3. **6技法で観点を出す**
   - `references/techniques.md` を読み、対象に合う形で6技法を適用する。
   - 各技法は「適用」「該当なし」「補助」のいずれかで扱う。
   - 「該当なし」の場合は `該当なし: <1行理由>` のみを書く。
   - 「補助」の場合は `補助: ` と明記し、1〜2件だけ挙げる。

4. **チェックリストで補完する**
   - API、サーバーサイド、ユースケース層なら `references/checklist-api.md` を読む。
   - 画面、フォーム、コンポーネントなら `references/checklist-ui.md` を読む。
   - 事故パターン確認のため、必ず `references/danger-patterns.md` を読む。
   - チェックリストは全部貼らず、対象に該当する項目だけ抽出する。

5. **テストケース一覧に落とす**
   - `references/output-format.md` の形式で出力する。
   - 最後に「まとめ：実装すべきテストケース一覧」を作る。
   - 各ケースには、入力、期待結果、由来した技法を含める。

6. **ユーザー確認を待つ**
   - 観点を提示した後、勝手にテストコードを書き始めない。
   - ユーザーが実装を依頼した場合だけ、選ばれた観点に沿ってテストを書く。

## 使わない場面

- ボタン色変更など、テスト観点を分解する価値がほぼない変更。
- 純粋なリファクタリングで、既存テストが十分にあり振る舞いが変わらない場合。
- ユーザーが明示的に「観点は不要、コードだけ」と指定した場合。

その場合でも、重大な事故パターンが見えるときは短く注意点を伝える。
