# 文書種別ごとの重点

文書種別に合う目的と読み手の行動を優先する。ここにない文書は、用途の近い型を選ぶ。

## 技術ブログ・解説記事

読者が問題を理解し、同じ方法を試すか避けるか判断できるようにする。

- 一般論より、扱う問題、観測、問いを早めに示す。
- 手順だけでなく、採用理由、適用条件、失敗例、使わなかった選択肢を残す。
- 調べた事実、自分の観測、推測を区別する。
- 実測していない性能や効果を断定しない。

## 設計メモ・意思決定記録

背景、制約、選択肢、判断、未決事項を後から追えるようにする。

- なぜ今決める必要があるかを示す。
- 採用案、代替案、判断理由を対応づける。
- 理想論ではなく、今回の制約と影響範囲に結びつける。
- リスク、未検証事項、今後の確認を決定済み事項と分ける。

## PR説明・変更概要

レビュアーが変更理由、差分、影響範囲、確認方法を短時間で把握できるようにする。

- 変更の背景または問題を先に置く。
- 実装詳細は、レビューしてほしい判断と差分を中心にする。
- テスト、コマンド、画面など、実行できる確認方法を示す。
- 対象外と未確認範囲を分け、変更していない箇所を保証しない。

## 社内告知・運用連絡

対象者が変更内容、必要な行動、期限、問い合わせ先を理解できるようにする。

- 誰が、いつまでに、何をするかを早めに示す。
- 例外、影響、問い合わせ先を曖昧にしない。
- 丁寧さを保ちつつ、行動に関係しない前置きを減らす。
- 情報がない期限や問い合わせ先を補わず、確認事項にする。

## レビューコメント

相手が問題と理由を理解し、次の修正を判断できるようにする。

- 指摘対象、問題が生じる理由、修正案の順に書く。
- 人ではなく、コード、仕様、挙動へ指摘を向ける。
- 代替案が複数ある場合は、推奨と判断基準を示す。
- 確信が低い場合は、断定せず確認依頼にする。

## リリースノート

利用者が変更内容と自分への影響を理解できるようにする。

- 利用者から見える変更を具体的に示す。
- 利用方法、互換性、移行、制約など必要な情報を優先する。
- 根拠のない価値表現より、何ができるようになったかを書く。
