# 概要

AIが読むものはMarkdown、人間がレビュー・比較・共有するものはHTML、という基準で成果物の形式を決める。HTMLにする場合は、内容規模に応じて構成テンプレートを選び、SVG図・色分けテーブル・カードなどの**視覚化要素**で「読まなくても構造が分かる」状態に仕上げる。外部依存のない単一HTMLファイルにする。

**markdownを `<h2>` `<p>` `<ul>` に置き換えただけのHTMLは禁止。** 文字情報を減らし、図・表・カード・色分けで構造を伝える。

# 使用タイミング

- ユーザーがプラン、Issue、レビュー結果、調査メモ、議事録、ポストモーテム、教育資料を人に共有しやすい形へ整えたい時
- ユーザーが「HTML化」「人間向け資料」「共有用ページ」「レビュー用ページ」「見やすく整理」と依頼した時
- 他スキルがMarkdownの設計プランやIssue本文を作成した後、人間向けHTMLも作るか確認して承諾された時
- 成果物をMarkdownのままにするべきか、HTMLにするべきか判断が必要な時

# Agentが行うこと

1. 成果物の主な読者がAIか人間かを判定する。
2. Markdownのまま残すべき場合は、HTML化しない理由を短く伝える。
3. 人間向けHTMLが有効な場合は、内容規模からHTMLテンプレートを1つ選ぶ。
4. 入力素材を人間が読む順序へ再構成する。**入力素材に書かれていない事実情報（担当者名、Slack/チケットID、重大度ラベル、コード断片、URL、数値、状態など）を視覚化のために創作してはいけない。** 視覚化コンポーネントを埋めるための情報が素材に無い場合は、その箇所を省略するか、`不明 (要追記)` のように欠落であることを明示する。
5. 成果物の種別（プラン / レビュー / ポストモーテム / 教育資料 等）から、組み込むべき**視覚化コンポーネント**を選ぶ。テンプレートの必須視覚化（scroll-report 等）と「成果物種別ごとの推奨」表は **和集合** をカバーする — **テンプレ必須にあって推奨セットに無い項目（例: tabbed-workspace の Before/After）も、推奨セットにあってテンプレ必須に無い項目（例: ポストモーテムのタイムライン）も、両方とも入れる**。テンプレ必須は最低ライン、成果物別推奨は固有の追加要求。重複するコンポーネント（例: 両方が TL;DR を要求）は1つに統合してよい。
6. `mkdir -p ./output` で保存先を用意し、`./output/{slug}.html` に単一HTMLファイルを作成する。
7. 生成後、保存先・選んだテンプレート・使用した視覚化コンポーネントを報告する。**素材にない情報を `不明 (要追記)` で表示した場合は、その箇所をユーザーへの報告で 1 行明示する。**

# 入力 / 出力

## 入力

- Markdown原稿、設計プラン、GitHub Issue本文、PR/レビューまとめ、議事録、調査メモ
- 共有対象、想定読者、用途、必要なら作成済みIssueやPRのURL
- 他スキルから連携される場合は、確定済み `<proposed_plan>` と作成済みIssue本文

## 出力

- Markdown継続を推奨する場合: 理由と次アクション
- HTMLを生成する場合: `./output/{slug}.html`
- 完了報告: 選択テンプレート、保存先、使用した視覚化コンポーネント、主な構成

## 入力素材が不足している場合

- HTML生成を明示されていても、本文・原稿・Issue本文などHTMLに入れる実素材がない場合は、ファイルを作らず「生成方針サマリ」を返す。
- 生成方針サマリには、HTML化する/しないの判断、選択テンプレート、想定する視覚化コンポーネント、想定保存先、主な構成、実素材が必要である旨を含める。
- 実素材不足を理由に生成方針サマリで止める判断は、例外処理として明示されているため、不明瞭点ではなく実行結果として扱う。
- 実素材がある場合は、方針サマリだけで止めずに `./output/{slug}.html` を作成する。

# 形式判断

## Markdownのままにする

次のいずれかに当てはまる場合は、HTML化を提案しない。

- `AGENTS.md`、`CLAUDE.md`、AIに常時読み込ませるプロジェクト指示
- `plan.md`、調査ダンプ、agent間の中間成果物
- ADR、仕様書、規約など、PRで行単位の差分レビューを重視する文書
- ターミナルの `cat` / `less` やプレーンテキストエディタで読む短いメモやチェックリスト

## HTMLを提案する

次のいずれかに当てはまる場合は、HTML化を提案する。ユーザーがHTML生成を明示している場合は、確認を挟まず生成する。

- 人間がレビュー、比較、意思決定する資料
- 経営層、他部署、チームメンバーへ共有するレポートやキックオフ資料
- 設計レビュー、コードレビュー、PRサマリー、障害ポストモーテム
- 長い解説記事、教育資料、オンボーディング資料
- UIや操作感を伝える軽量プロトタイプ、簡易エディタ、ダッシュボード

# HTMLテンプレート選択

## Small: `single-screen-brief`

- 条件: 4セクション以下、表やコードがほぼない、短い共有・意思決定メモ
- 構成: 1画面で要点が見えるペライチ。タイトル、TL;DRカード、主要ポイント（カード化）、次アクション（ステップカード）を上から順に置く
- 必須視覚化: TL;DRカード（色枠付き）+ 主要ポイントの3〜4カードグリッド + 次アクションのステップカード
- 制約: タブやアコーディオンを使わない。縦スクロールは最小限にする

## Medium: `scroll-report`

- 条件: 5〜10セクション程度、説明・表・コードを含む設計整理やレビューまとめ
- 構成: 縦スクロール前提の読み物。冒頭にTL;DRカードと目次、本文に視覚化セクションを縦に並べる
- 必須視覚化: TL;DRカード + SVG図 1点以上（フロー図 or 構造図）+ 色分けテーブル 1点以上 + ステップカード + 根拠/参照テーブル
- 制約: ページ切り替えUIは原則使わない。比較や補足が多い場合だけアコーディオンを使う

## Large: `tabbed-workspace`

- 条件: 10セクション超、複数観点、長いコード・表・時系列・Before/Afterを含む大きなレビュー資料
- 構成: タブで概要、設計、詳細、テスト、補足などを切り替える。必要に応じてタブ内に目次やアコーディオンを置く
- 必須視覚化: 概要タブにTL;DRカード + SVG図2種類以上（経路/構造/時系列/状態遷移から2種）+ 色分けテーブル2種類以上 + Before/After二段組 + ステップカード + 根拠表
- 制約: 初期表示は概要タブにする。最初の画面だけで全体像と読む順序が分かるようにする
- タブ粒度: 4〜6個を目安に、読者の目的別にまとめる。例: ポストモーテムは「概要」「時系列」「原因と対応」「再発防止」「証跡/付録」。証跡やログは単独で探す需要が高い場合だけ別タブにする。固定タブ名に合わせるより、読者の探索目的で統合/分割を決め、完了報告でその理由を1行添える。

## 判定ルール

- 迷う場合は `scroll-report` を選ぶ。
- タブが必要なほど観点が分かれている場合は、文字量が中程度でも `tabbed-workspace` を選ぶ。
- 1画面に詰めると可読性が落ちる場合は、`single-screen-brief` ではなく `scroll-report` を選ぶ。
- 内容の規模より、読者の操作負荷と情報探索のしやすさを優先する。

# 視覚化コンポーネント

HTML出力には、成果物の種別に応じて以下のコンポーネントを組み合わせる。**文字段落だけで構成してはいけない。**

## TL;DRカード（全テンプレート必須）

- 画面冒頭に1枚。要点を2〜3行で言い切る。
- 結論・原因・推奨アクションなど、性質に応じて**色枠**で区別する。
  - 結論/原因: 赤枠（`--ng`）の `.root-cause`
  - 推奨アクション/解消: 緑枠（`--ok`）の `.fix-callout`
  - 注意/仮説: 黄枠（`--warn`）

## SVG図（scroll-report は1点以上、tabbed-workspace は2点以上）

用途別に使い分ける。inline `<svg>` で box + arrow を描画。外部画像は使わない。

| 図の種類 | 使う場面 |
|---------|---------|
| **フロー図 / 経路図** | 処理の流れ、リクエスト経路、ユーザー導線。失敗箇所を赤、成功を緑で塗る |
| **構造図 / データモデル図** | コンポーネント関係、エンティティ関連、依存関係。完了は緑実線、未実施は赤破線 |
| **状態遷移図** | 状態の変化、ライフサイクル |
| **タイムライン** | 障害の時系列、マイルストーン、リリース計画 |
| **概念図** | 教育資料、用語の関係性 |

### SVG マーカー（必須）

```xml
<defs>
  <marker id="arr-ok" viewBox="0 0 10 10" refX="9" refY="5" markerWidth="8" markerHeight="8" orient="auto">
    <path d="M0,0 L10,5 L0,10 z" fill="#1f883d"/>
  </marker>
  <marker id="arr-ng" viewBox="0 0 10 10" refX="9" refY="5" markerWidth="8" markerHeight="8" orient="auto">
    <path d="M0,0 L10,5 L0,10 z" fill="#cf222e"/>
  </marker>
</defs>
```

成功経路は実線+`arr-ok`、失敗・欠落は破線（`stroke-dasharray="5 3"`）+`arr-ng`。

### レイアウト指針

- フロー図: 横一列に4〜5ボックス。失敗ポイントは赤い箱+番号付き矢印。ビューポート目安 `viewBox="0 0 880 360"`
- 構造図: 3〜4エンティティを横並び。下部に黄色枠で「ここが切れている」など1文添える

## 色分けテーブル（scroll-report / tabbed-workspace 必須）

文字だけのテーブルは禁止。行ごとに状態色を付ける。

| 用途 | 列の例 |
|------|--------|
| **状態テーブル** | 操作 / 副作用 / 目的への寄与 / 状態（✓済 ✗未実施 ✗NG）|
| **比較テーブル** | 観点 / 案A / 案B / 推奨 |
| **根拠テーブル** | 事実 / ファイル:行 / タグ（fact/fix/issue）|
| **観点別チェック** | 観点 / 期待 / 実態 / 判定 |

行に `class="done"`（緑）/ `class="gap"`（赤）/ `class="warn"`（黄）を付けて背景を着色する。

## ステップカード（全テンプレート必須）

手順・タスク・次アクションは**箇条書きにせず**、番号付きカードをグリッドで並べる。

- `.steps` グリッド + `.step .num` の丸番号
- 各カードに見出し（短い動詞句）+ 1〜2行の補足

## Before/After 二段組（変更がある成果物で推奨）

`.twocol` で左右に並べる。コード差分、UI変更、設定変更、運用フロー変更などで使う。

## 根拠/参照テーブル（調査・レビュー系で必須）

ファイル:行、URL、コミットハッシュなどの根拠は、`<ul>` の箇条書きで並べず**必ずテーブル化**する。タグで種別を区別する（青=fact、緑=fix、赤=issue）。

## サマリーカード / 統計バー（ダッシュボード・ポストモーテム向け）

- 数値KPIは大きな文字+小さなラベルの**カード**で表示
- 影響範囲・進捗率などはバーやドーナツで視覚化

## 成果物種別ごとの推奨コンポーネント

| 成果物 | 必ず入れる |
|--------|-----------|
| 設計プラン | TL;DR + 構造図 + ステップカード + 比較テーブル |
| Issue / PRレビュー | TL;DR + 状態テーブル + 根拠テーブル + Before/After |
| ポストモーテム | TL;DR + タイムライン + 原因経路図 + 対応ステップカード + 再発防止テーブル |
| 教育・オンボーディング | 概念図 + ステップカード + 用語テーブル |
| 障害・不具合調査 | TL;DR + 経路図 + データモデル図 + 状態テーブル + 根拠テーブル |
| ダッシュボード | サマリーカード + 統計バー + 状態テーブル |

# CSS / SVG スターターキット

## カラーパレット（CSS変数・必須）

```css
:root {
  --ok: #1f883d;       /* 完了・成功 */
  --ok-bg: #dafbe1;
  --ng: #cf222e;       /* 失敗・未実施 */
  --ng-bg: #ffebe9;
  --warn: #bf8700;     /* 仮説・注意 */
  --warn-bg: #fff8c5;
  --accent: #0969da;   /* 情報・リンク */
  --accent-bg: #ddf4ff;
}
```

ダークモード時はこれらの背景を `prefers-color-scheme: dark` 内で適切に上書きする。

## 全体構造の参考（scroll-report の場合）

```
<header.hero>     ← グラデ背景・タイトル・サブタイトル
<card #1>         ← TL;DR（結論を2〜3行で）
<card #2>         ← SVG図 ① フロー / 経路 / 構造
<card #3>         ← 色分けテーブル（状態 or 比較）
<card #4>         ← ステップカード（手順・次アクション）
<card #5>         ← Before/After（変更がある場合）
<card #6>         ← 根拠/参照テーブル
<card #7>         ← 副次仮説 / 補足（黄色枠）
```

# NGパターン

次のHTMLは作らない。生成前後にセルフチェックする。

- markdown の見出しをそのまま `<h1>` `<h2>` に変換しただけ
- 図が一切ない（文字だけ）
- 色分けがない（全部黒文字、全部同じ背景）
- 箇条書き（`<ul>` `<li>`）が大量に並ぶだけ
- ファイル:行 や 参照URL が `<ul>` の箇条書きで並ぶだけでテーブル化されていない
- 手順が `<ol>` のテキストリストで、ステップカード化されていない
- TL;DRカードがなく、結論が文章の途中に埋もれている
- **入力素材に書かれていない事実情報を視覚化のために創作している**（担当者名、Slack/チケットID、重大度ラベル、コード断片、URL、状態、KPI数値などを推測で埋める）。視覚化を成立させたい欲求が、ハルシネーションの最大の動機になる

# HTML作成ルール

- 保存先は `./output/{slug}.html` にする。
- 書き込み前に `mkdir -p ./output` を実行し、初回生成でも失敗しないようにする。
- `{slug}` は内容から英小文字とハイフンで分かりやすく命名する。
- HTML / CSS / JavaScript / SVG はすべて1ファイル内に含める。
- 外部CDN、外部フォント、外部画像、外部スクリプトは使わない。図はinline SVGで描画する。
- `viewport` metaを設定する。
- フォントは `system-ui`, `"Hiragino Sans"`, `"Yu Gothic"`, sans-serif を指定する。
- `prefers-color-scheme` でダークモードに対応する。
- 見出し階層は `h1`、`h2`、`h3` の順で自然に整理する。
- コントラスト、余白、行間は読みやすさを優先する。
- 色だけで意味を伝えない（アイコン・記号・ラベルで補強する。色覚多様性対応）。
- 画像を使う場合は `alt` を付ける。SVGには `<title>` または `aria-label` を付ける。
- JavaScriptを使う場合は、タブやアコーディオンなど必要な操作だけに限定する。
- 元のMarkdownをそのままHTMLへ逐語変換せず、人間が読む順序に再編集する。文字段落は最小限にし、視覚化コンポーネントに置き換える。

# GitHub Issue連携時の扱い

- Issue作成フローから呼ばれた場合は、確定済み `<proposed_plan>` と作成済みIssue本文を入力素材にする。
- Issue本文は実装者向けMarkdownとして尊重し、HTML側では人間のレビュー・共有用に**要約カード、比較テーブル、ステップカード、論点の状態テーブル**を前面に出す。
- Issue URLがある場合は、HTMLの冒頭または末尾に関連リンクとして置く。
- HTML生成の承諾が曖昧な場合は生成しない。直前の確認に対する `OK`、`お願いします`、`作って`、`yes` などの明確な承諾だけで生成する。

# 品質チェック

## 形式判断

- [ ] Markdownのままにするべき成果物を無理にHTML化していない
- [ ] HTML生成時にテンプレートを1つだけ選んでいる
- [ ] 選んだテンプレートの条件、構成、制約に合っている

## 視覚化（最重要）

- [ ] TL;DRカードが画面冒頭にあり、2〜3行で結論を言い切っている
- [ ] テンプレートに応じた必須視覚化コンポーネントが入っている
  - single-screen-brief: カードグリッド + ステップカード
  - scroll-report: SVG図 1点以上 + 色分けテーブル + ステップカード + 根拠表
  - tabbed-workspace: SVG図 2点以上 + 色分けテーブル 2種 + Before/After + ステップカード + 根拠表
- [ ] 「成果物種別ごとの推奨コンポーネント」表の項目もテンプレ必須に上乗せして入っている（両者の和集合）
- [ ] 文字段落の連続でセクションを構成していない
- [ ] テーブルは状態色（done/gap/warn）で行が着色されている
- [ ] 手順は `<ol>` ではなくステップカードになっている
- [ ] ファイル:行や参照URLはテーブル化されており箇条書きではない
- [ ] 成功/失敗・完了/未実施が色 **と** ラベル/記号の両方で識別できる

## 素材忠実性（重要）

- [ ] 入力素材に書かれていない事実情報を、視覚化のために創作していない
- [ ] 情報が素材に無い箇所は、`不明 (要追記)` などで欠落を明示してある（黙って埋めない）
- [ ] 完了報告で「素材にない箇所をどう扱ったか」を 1 行で明示している

## 技術要件

- [ ] `./output/{slug}.html` に保存している
- [ ] 保存前に `mkdir -p ./output` で出力先を用意している
- [ ] 外部CDN、外部フォント、外部画像、外部スクリプトを使っていない
- [ ] CSS変数 `--ok / --ng / --warn / --accent` を定義している
- [ ] SVGに矢印マーカー（`arr-ok` / `arr-ng`）を定義している
- [ ] ダークモード、viewport、日本語向けフォント、見出し階層、コントラストを満たしている
- [ ] 画像があれば `alt`、SVGに `<title>` または `aria-label` を付けている
- [ ] JavaScriptはタブやアコーディオンなど必要な操作だけに限定している
- [ ] 人間向けに読む順序を再構成している
