# Recheck Workflow

## 対象

- この会話でこのスキルが以前に投稿した指摘だけを対象にする。
- 他者のコメント、別会話のコメント、再チェック中に新しく見つけた論点は含めない。
- 最新の PR 情報、差分、現在のコード、review threads を再取得する。
- 既に Resolve 済みの thread は対象外にする。

前回コメントは次の順で thread と対応付ける。

1. 会話内の comment URL または comment ID。
2. 現在の認証ユーザー、AI 識別メタ情報、ファイルパスが一致するコメント。
3. コメントの論点と差分文脈が一致するコメント。

## 判定方法

元コメントから、指摘していた発生条件、原因、問題となる挙動、影響を再構成する。
変更行の有無ではなく、その失敗条件が現在のコードで到達可能かを確認する。

- `resolved`: 元の失敗条件が閉じ、同じ原因から問題となる挙動へ到達しない。
- `partial`: 一部の条件は閉じたが、元コメントに含まれる別の入力、状態、経路が残る。
- `unresolved`: 元の失敗条件がそのまま残る、または修正が別の場所に移しただけで影響が残る。
- `unknown`: 最新コード、実行時条件、仕様、権限の不足により根拠付きで判定できない。

テスト追加だけで `resolved` としない。
実装が失敗条件を閉じていることを確認し、テストはその裏付けとして扱う。

## アクション

- `resolved`: 改善済みである根拠を短く返信し、thread を Resolve する。
- `partial` / `unresolved`: 残っている発生条件と挙動を同じ thread へ返信する。
- `unknown`: 判断できない理由をチャットで報告し、Resolve しない。
- 返信できない場合だけ、必要に応じて overall comment で状態を伝える。
- 返信には `references/posting-rules.md` の再チェック用 AI 識別メタ情報を付ける。
- 再チェック依頼を返信と Resolve の許可として扱い、投稿前確認は挟まない。

## 最終報告

- 再コメント件数、Resolve 件数、overall comment 件数を伝える。
- 未解決または判断不能があれば、その条件と理由を伝える。
