# Posting Rules

## コメント本文

- 曖昧な表現を避け、何が問題で、なぜ問題かを簡潔に書く。
- 可能なら修正方針や代替案も添える。
- 不要に高圧的な表現は避ける。
- `must` 以外は、必須ではないことが伝わる書き方にする。
- コメントは短く具体的にする。
- 1コメント1論点を基本とする。
- 断定しすぎる必要がない論点は、推奨や質問として表現する。
- 既存実装やプロジェクト規約を根拠にできる場合は、それを短く添える。

## AI エージェント識別メタ情報

- AI エージェントが投稿したレビューであることを、各コメント本文だけで判別できるようにする。
- メタ情報には少なくとも AI エージェントによる投稿だと分かる文言を含める。
- メタ情報はコメントごとに欠けなく付ける。overall review comment のみで代用しない。
- モデル名を確実に特定できる場合は含める。特定できない場合は含めない。
- エージェント名は必須にしない。実行主体を明示する必要がある場合だけ、実際にレビューを投稿した主体名を括弧で添える。
- モデル名を含める場合は、実際に使用したモデル名に差し替える。
- プレースホルダーをそのまま投稿しない。投稿前に実際のエージェント名へ置換する。
- モデル名を含める場合の推奨フォーマットは `AIレビュー補助（<Agent Name> / <Model Name>）によるコメントです 🤖` とする。
- モデル名を含めない場合のみ `AIレビュー補助によるコメントです 🤖` を使う。
- 通常レビューでもモデル名が特定できる場合は、可能な限りモデル名を含めたフォーマットを優先する。
- 再チェックでも、モデル名を確実に特定できる場合は含める。特定できない場合は含めない。
- 再チェックでモデル名を含める場合の推奨フォーマットは `AIレビュー補助（<Agent Name> / <Model Name>）による再チェックコメントです 🤖` とする。
- 再チェックでモデル名を含めない場合のみ `AIレビュー補助による再チェックコメントです 🤖` を使う。
- 既存運用で別フォーマットが必要な場合も、人間レビューと見分けられることを優先する。

## 本文の渡し方

- 改行が必要な場合は、送信 payload に実改行を含む本文を使い、`\n` を見た目のまま投稿しない。
- 投稿前に、コメント本文に文字列としての `\n` が残っていないことを確認する。
- 複数行コメントや Markdown コメントは、一時ファイル、JSON ファイル、または `gh api --field body=@file` のようなファイル参照で渡す。
- バッククォート、`$()`、引用符、改行を含む本文をシェル引数へ直接埋め込まない。

## 投稿後確認

- 投稿後は `gh api` または `gh pr view --comments` で、意図した本文が実際に投稿されていることを確認する。
- 投稿本文が崩れている、AI 識別メタ情報が欠けている、または `\n` が文字列として出ている場合は、修正方針をユーザーへ報告する。
