# Posting Rules

## コメント本文

- PR 本文と同じ言語で書く。本文で判別できなければタイトル、それでも不明なら日本語を使う。
- 1コメントにつき、同じ原因と修正方針を持つ一つの論点だけを書く。
- 先頭に `references/review-criteria.md` のラベルを一つ付ける。
- 成立条件、具体的な問題、原因、影響を、判断に必要な範囲で短く書く。
- 修正方針が一意または理解に必要な場合だけ、修正案を添える。
- 未確認の仕様や実行時条件に依存する場合は、その条件を明記して `[ask]` にする。
- `[must]` 以外は、必須、推奨、質問、提案の違いが文面から分かるようにする。
- 「重要です」「懸念があります」など、論点を増やさない前置きや総括を書かない。
- 差分の要約、称賛だけのコメント、想像上の読者との問答を投稿しない。

指摘なしの review comment は重要度ラベルを付けず、確認した範囲で修正必須の指摘がなかったことだけを書く。
PR approval と誤解される表現は避ける。

## AI 識別メタ情報

- 各 inline comment、overall comment、指摘なし comment にメタ情報を付ける。
- エージェント名とモデル名は、実行中の環境から取得する。取得できた値をそのまま使う。
- メタ情報は `AIレビュー補助<識別子>による<種別>です 🤖` の形式とする。
  - `<識別子>`: 取得できた識別情報を ` / ` で結合し `（...）` で囲う。エージェント名もモデル名も取得できない場合は空文字列とする。
  - `<種別>`: 通常レビューなら `レビュー`、再チェックなら `再チェックコメント` とする。
- 特定のエージェント名、固定パス、プレースホルダー、古い固定モデル名を投稿しない。

## 本文の渡し方

- 複数行 Markdown は一時ファイルまたは JSON payload で渡す。
- バッククォート、`$()`、引用符、改行を含む本文をシェル引数へ直接埋め込まない。
- 実改行を使い、文字列としての `\n` を投稿しない。
- 投稿前のユーザー確認は不要。

## 投稿後確認

- API 応答または再取得で、本文、ラベル、メタ情報、コメント位置を確認する。
- 本文崩れ、メタ情報欠落、リテラル `\n` があれば、可能なら修正 API で直す。
