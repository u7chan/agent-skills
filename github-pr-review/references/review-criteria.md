# Review Criteria

## 指摘の分類

各指摘の先頭に、次のラベルを一つだけ付ける。

- `[must]` ⚠️: 修正しないと、確認可能な条件で不具合、仕様逸脱、セキュリティ問題、データ破壊が起きる。
- `[should]` 💡: 動作は成立しても、根拠のある保守性、一貫性、運用上の問題が残り、放置コストが高い。
- `[nit]` ✏️: タイポ、文言、既存規約からの軽微な逸脱。
- `[ask]` ❓: 仕様、意図、実行時条件が不足し、問題かどうかを確定できない。
- `[imo]` 💭: 正誤ではなく、複数の妥当な選択肢がある提案。

`[must]` と `[should]` は、好みや未確認の推測には使わない。

## 投稿前の品質ゲート

指摘候補ごとに次を確認する。

1. **差分との関係**: PR が問題を導入または悪化させている。
2. **成立条件**: 入力、状態、権限、実行順序、環境、将来の変更など、問題が表面化する条件を具体化できる。
3. **具体的な問題**: 条件成立時の誤動作、または保守・運用コストを説明できる。
4. **因果**: 差分のどの処理や構造が、なぜその問題を起こすか説明できる。
5. **影響**: 利用者、データ、運用、後続処理、変更容易性の何へ影響するか説明できる。
6. **範囲**: 確認した事実を超えて、別ケースやコード全体へ一般化していない。
7. **反証確認**: 呼び出し元、ガード、型、フレームワーク仕様、テストにより既に防がれていない。

1から5のいずれかを説明できない場合は、追加調査する。
調査しても仕様や実行時条件が不足する場合は `[ask]` に落とすか、投稿しない。

## 事実と不確実性

- コード、差分、テスト、仕様から確認した内容を事実として書く。
- 実行環境や仕様を仮定する場合は、その条件をコメント内へ明記する。
- 「可能性がある」だけでは指摘にしない。到達可能な失敗経路または具体的な変更コストを示す。
- 複数の原因や失敗経路を一つの問題としてまとめない。修正方法や影響が異なるならコメントを分ける。
- 「必ず防げる」「保証する」「解決する」は、成立条件を確認できる場合だけ使う。
- 例が主張の一部しか支えない場合は、主張をその例の範囲まで狭める。

## 優先して確認する観点

- **正しさ**: 境界値、null/空値、例外経路、状態更新、ロールバック、数値計算。
- **契約**: API、型、スキーマ、後方互換性、既存仕様との不一致。
- **セキュリティ**: 入力検証、認証、認可、機密情報、インジェクション。
- **並行性と運用**: 二重実行、冪等性、競合、タイムアウト、リトライ、リソース解放。
- **データ量**: N+1、無制限取得、不要な I/O、現実的な本番データでの劣化。
- **保守性**: 責務、依存方向、既存規約との一貫性、変更理由の局所化。
- **テスト**: PR が変更した振る舞いと、再発しうる失敗条件の未検証。

対象に関係する観点だけを使い、チェックリストを埋めるための指摘は作らない。

## 投稿しないもの

- 差分の要約、一般的な称賛、説明だけのコメント。
- プロジェクト規約や実害に結び付かない好み。
- 到達条件を示せない仮想的な不具合。
- PR が触れていない既存問題。
- 同じ原因と失敗条件を言い換えただけの重複指摘。
