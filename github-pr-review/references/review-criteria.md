# Review Criteria

## コメント分類

- `[must]` ⚠️
  - 修正必須。
  - バグ、仕様逸脱、セキュリティ懸念、重大な設計不整合、将来的に高確率で障害につながる問題。

- `[should]` 💡
  - 強く修正を推奨。
  - 可読性・保守性・一貫性・拡張性の観点で問題があり、放置コストが高いもの。

- `[nit]` ✏️
  - 軽微な指摘。
  - タイポ、文言、コメント表現、細かな命名やフォーマットの違和感。

- `[ask]` ❓
  - 質問・確認。
  - 意図、仕様、背景、将来想定などの確認が必要な場合。

- `[imo]` 💭
  - 提案。
  - チーム方針や好みに依存しやすく、採否が分かれうる改善案。

## レビュー観点

### 1. 正しさ

- 仕様どおりに動作するか。
- 明らかなバグや漏れがないか。
- 境界値、例外系、NULL/空値、未定義ケースが考慮されているか。

### 2. 設計

- 責務分離が適切か。
- 依存方向に無理がないか。
- 命名がドメインや責務を正しく表しているか。
- その場しのぎの実装になっていないか。

### 3. 可読性・保守性

- 意図がコードから読み取りやすいか。
- 関数やクラスが長すぎないか。
- 重複や密結合が増えていないか。
- 将来の変更に弱い構造になっていないか。

### 4. 一貫性

- 既存コードやプロジェクト規約と揃っているか。
- 命名、例外処理、責務の置き方、テスト方針に一貫性があるか。

### 5. テスト

- 変更に対して必要なテストがあるか。
- 正常系だけでなく異常系・境界値も必要に応じてカバーされているか。
- テストしづらい設計になっていないか。

### 6. パフォーマンス・運用

- 不要なループ、N+1、重複計算、無駄な I/O がないか。
- ログ、監視、エラーハンドリングの観点で問題がないか。

### 7. セキュリティ

- 入力値検証が不足していないか。
- 権限や認可の考慮漏れがないか。
- 機密情報の扱いに問題がないか。

## コメント文例

- `[must] ⚠️ この分岐だと xxx の場合に null 参照になるため、ガードが必要です。`
- `[should] 💡 この関数は責務が2つ入っているので、yyy の処理は分離したほうが保守しやすいです。`
- `[nit] ✏️ コメントの文言は「取得する」より「読み込む」のほうが他箇所と揃っています。`
- `[ask] ❓ このケースを許容している意図はありますか。仕様なら問題ありません。`
- `[imo] 💭 個人的にはこのロジックは service 側に寄せたほうが自然に見えます。`
