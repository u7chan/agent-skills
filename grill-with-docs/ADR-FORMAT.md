# ADR（Architecture Decision Record）

ADR は、重要な設計上の意思決定とその理由を記録するための短いドキュメントである。

## 目的

将来の開発者が「なぜこの選択をしたのか」を理解できるようにする。

ADR は設計書ではない。詳細な調査結果や実装内容ではなく、意思決定とその背景のみを記録する。

## 配置場所

`docs/adr/`

ファイル名は連番で管理する。

```text
docs/adr/
├── 0001-monorepo.md
├── 0002-postgresql.md
└── 0003-keycloak.md
```

## テンプレート

```md
# ADR-XXXX: {決定事項}

{何を決めたか。}

{なぜそうしたか。代替案との比較を含めて1〜3文で記載する。}
```

### 例

```md
# ADR-0001: PostgreSQLを採用する

アプリケーションのメインDBとしてPostgreSQLを採用する。

SQLiteも検討したが、将来的な同時書き込み性能と運用性を考慮してPostgreSQLを選択した。
```

## 運用ルール

- ADR は採択済みの意思決定だけを書く
- ADR は「何を決めたか」と「なぜ決めたか」だけを書く
- 5〜15行程度を目安とする
- 詳細な設計や調査内容は Issue・設計書・PR に残す
- 将来「なぜこの選択をしたのか」が分かれば十分
- 覆しにくい意思決定のみ ADR 化する
- 差し替えが軽いライブラリや開発ツールは ADR 化しない
- 決定を置き換える場合は、既存 ADR のステータス管理ではなく、新しい ADR の本文で旧 ADR との関係を書く

## ADR を作成する条件

以下をすべて満たす場合のみ ADR を作成する。

1. 後から変更するコストが高い
2. 理由を知らないと不自然に見える
3. 複数案のトレードオフを経て決定した

## ADR の例

- モノレポ採用
- PostgreSQL採用
- Keycloak採用
- OAuth2 Proxy採用
- オンプレ運用を選択
- イベント駆動アーキテクチャ採用
- WASM Sandbox採用

## ADR 化しない判断

以下は ADR にしない。

- 流行っている、標準的、慣れている、という理由だけの採用
- 局所的なライブラリや開発ツールの採用
- 差し替えコストが低い選定
- README・Issue・PR の説明で十分な選定
- プロジェクト全体の構造、運用、設計方針を縛らない選定

ただし、その選定が CI、開発手順、設計方針、画面実装、運用手順などを広く縛る場合は ADR 候補にする。

## 任意項目

必要な場合のみ以下を追加してよい。

```md
## Considered Options

- Option A
- Option B

## Consequences

- 想定される影響
```

これらは将来の判断材料として価値がある場合のみ記載し、形式的に追加しないこと。
