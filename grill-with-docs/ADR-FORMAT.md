# ADRのフォーマット

ADR（Architecture Decision Record／アーキテクチャ意思決定記録）とは、重要な設計上の意思決定とその背景・理由を、決定が行われた時点のまま記録に残す短いドキュメントです。

ADRは `docs/adr/` 配下に置き、連番で命名します（`0001-slug.md`、`0002-slug.md`、…）。

`docs/adr/` ディレクトリは必要になったときだけ作成してください——最初のADRが必要になった瞬間で構いません。

## テンプレート

```md
# {決定の短いタイトル}

{1〜3文：どんな状況で、何を決め、なぜそうしたのか}
```

これだけです。ADRは一段落で済んで構いません。価値があるのは、決定が「行われたこと」と「その理由」を残すことであって、セクションを埋めることではありません。

## 任意セクション

本当に価値を加える場合だけ書き添えてください。ほとんどのADRには不要です。

- **Status** フロントマター（`proposed | accepted | deprecated | superseded by ADR-NNNN`）——決定を見直す可能性があるときに便利
- **Considered Options** ——却下した代替案を記録に残す価値があるときだけ
- **Consequences** ——明白でない波及効果に注意を促す必要があるときだけ

## 連番の付け方

`docs/adr/` を走査して既存の最大番号を見つけ、1を足してください。

## ADRを提案すべきとき

以下の三つすべてが当てはまる場合に限ります。

1. **覆しにくい** — 後から考えを変えるコストが無視できない
2. **背景なしでは意外に映る** — 将来の読み手がコードを見て「いったいなぜこんなやり方を？」と首を傾げる
3. **本物のトレードオフの結果である** — 実在する選択肢の中から、明確な理由で一つを選んでいる

簡単に覆せる決定なら見送ってください——いずれ覆すだけです。意外性がなければ誰も疑問に思いません。実質的な代替案がなかったなら、「当たり前のことをした」以上に記録すべきものはありません。

### ADRに値するもの

- **アーキテクチャの骨格。**「モノレポを採用する」「書き込みモデルはイベントソースで、読み取りモデルはPostgresに射影する」
- **コンテキスト間の統合パターン。**「OrderingとBillingは同期HTTPではなくドメインイベントで通信する」
- **ロックインを伴う技術選定。** データベース、メッセージバス、認証プロバイダ、デプロイ先など。すべてのライブラリではなく、差し替えに四半期単位の労力がかかるものだけ。
- **境界とスコープに関する決定。**「顧客データはCustomerコンテキストが所有し、他のコンテキストはIDでのみ参照する」。「やらない」という明示的な決定は、「やる」と同じくらい価値がある。
- **当たり前の道筋からの意図的な逸脱。**「ORMではなく手書きSQLを使う。理由はX」。常識的な読み手なら逆を予想するようなものは何でも対象になる。これによって、後任のエンジニアが「直そう」とした結果、意図的な選択を壊してしまう事態を防げる。
- **コードからは見えない制約。**「コンプライアンス要件によりAWSは使えない」「パートナーAPIの契約上、応答時間は200ms未満でなければならない」
- **却下した代替案のうち、却下の理由が自明でないもの。** GraphQLを検討した上で微妙な理由でRESTを採った場合は記録すること——さもなければ半年後にまたGraphQLが提案される。
