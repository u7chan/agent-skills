# CONTEXT.md のフォーマット

## 構成

```md
# {コンテキスト名}

{このコンテキストが何であり、なぜ存在するのかを1〜2文で説明する}

## Language

**Order**:
{用語を1〜2文で説明する}
_Avoid_: Purchase, transaction

**Invoice**:
納品後に顧客へ送付する支払い請求。
_Avoid_: Bill, payment request

**Customer**:
注文を行う人または組織。
_Avoid_: Client, buyer, account
```

## ルール

- **言い切る。** 同じ概念に複数の語が存在するなら、最良の一つを選び、残りは避けるべき別名として列挙する。
- **衝突は明示的にフラグを立てる。** 用語があいまいに使われている場合は「Flagged ambiguities」に書き出し、解決方法をはっきり示す。
- **定義は引き締めて書く。** 最大でも1〜2文。「何である」かを定義し、「何をする」かは書かない。
- **関係性を示す。** 用語名は太字にし、明らかな場合は多重度（カーディナリティ）も書き添える。
- **このプロジェクトのコンテキストに固有の用語だけを載せる。** 一般的なプログラミングの概念（タイムアウト、エラー型、汎用的なユーティリティパターンなど）は、プロジェクト内で多用されていても載せない。用語を追加する前に自問してほしい——これはこのコンテキスト独自の概念か、それとも一般的なプログラミング概念か？ 載せるべきは前者だけだ。
- **自然なまとまりが見えてきたら、用語を小見出しでグループ化する。** すべての用語が一つの結束した領域に属しているなら、フラットなリストのままで構わない。
- **対話例を書く。** 開発者とドメインエキスパートの会話を載せ、これらの用語が自然にどう絡み合うかを示し、関連する概念どうしの境界を明確にする。

## 単一コンテキスト vs 複数コンテキスト

**単一コンテキスト（ほとんどのリポジトリ）：** リポジトリのルートに `CONTEXT.md` を一つ置く。

**複数コンテキスト：** リポジトリのルートに `CONTEXT-MAP.md` を置き、各コンテキストの所在と相互の関係を一覧にする。

```md
# Context Map

## Contexts

- [Ordering](./src/ordering/CONTEXT.md) — 顧客の注文を受け付け、追跡する
- [Billing](./src/billing/CONTEXT.md) — 請求書を生成し、支払いを処理する
- [Fulfillment](./src/fulfillment/CONTEXT.md) — 倉庫のピッキングと出荷を管理する

## Relationships

- **Ordering → Fulfillment**：Orderingが `OrderPlaced` イベントを発行し、Fulfillmentがそれを受けてピッキングを開始する
- **Fulfillment → Billing**：Fulfillmentが `ShipmentDispatched` イベントを発行し、Billingがそれを受けて請求書を生成する
- **Ordering ↔ Billing**：`CustomerId` と `Money` の型を共有する
```

スキルはどちらの構成かを次のように推測します。

- `CONTEXT-MAP.md` があれば、それを読んでコンテキストの所在を把握する
- ルートに `CONTEXT.md` だけがあれば、単一コンテキストとみなす
- どちらもなければ、最初の用語が確定したタイミングでルートに `CONTEXT.md` を作成する

複数のコンテキストが存在する場合、今話している話題がどのコンテキストに属するかを推測してください。判断がつかなければ尋ねてください。
