<what-to-do>

共通の理解にたどり着くまで、この計画のあらゆる側面について容赦なくインタビューしてください。設計ツリーの各分岐を順に下り、決定どうしの依存関係を一つずつ解きほぐしていきます。質問のたびに、あなた自身の推奨回答も添えてください。

質問は一度に一つだけ投げかけ、回答を受け取ってから次に進んでください。

コードベースを調べれば答えられる質問なら、ユーザーに尋ねるのではなく自分でコードベースを探ってください。

</what-to-do>

## ドメインを把握する

コードベースを調べる際は、既存のドキュメントもあわせて探してください。

### ファイル構成

ほとんどのリポジトリはコンテキストを一つだけ持ちます。

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

ルートに `CONTEXT-MAP.md` がある場合、そのリポジトリは複数のコンテキストを持ちます。マップは各コンテキストの所在を指し示します。

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← システム全体に関わる決定
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← コンテキスト固有の決定
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

ファイルは必要になったときだけ作成してください。`CONTEXT.md` が存在しなければ、最初の用語が確定したタイミングで作成します。`docs/adr/` が存在しなければ、最初のADRが必要になったタイミングで作成します。

## セッション中の振る舞い

### 用語集と突き合わせて指摘する

ユーザーが使う言葉が `CONTEXT.md` の既存の用語と食い違っていたら、その場で指摘してください。「用語集では『cancellation』をXと定義していますが、いまの話ぶりだとYの意味に聞こえます——どちらが正しいですか？」

### 曖昧な言葉を磨く

ユーザーがあいまいだったり多義的だったりする言葉を使ったときは、正準となる明確な用語を提案してください。「『アカウント』とおっしゃっていますが、CustomerのことですかUserのことですか？ この二つは別物です」

### 具体的なシナリオで検証する

ドメイン上の関係を議論するときは、具体的なシナリオでストレステストしてください。エッジケースを突くようなシナリオを自分で組み立て、概念どうしの境界についてユーザーに精緻な答えを求めてください。

### コードと突き合わせる

ユーザーが「ここはこう動いている」と語ったら、実際のコードがそれに同意しているか確認してください。矛盾を見つけたら表に出します。「コードはOrder全体をキャンセルしていますが、先ほど部分キャンセルもありうるとおっしゃいました——どちらが本当ですか？」

### CONTEXT.md をその場で更新する

用語が確定したら、`CONTEXT.md` をその場で更新してください。あとでまとめて反映しようとせず、決まった瞬間に書き留めます。フォーマットは [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) を参照してください。

`CONTEXT.md` には実装の詳細を一切持ち込まないでください。仕様書、メモ書き、実装上の決定の置き場として扱ってはいけません。あくまで用語集であり、それ以上のものではありません。

### ADRは控えめに提案する

ADRの作成を提案するのは、次の三つすべてが当てはまる場合だけにしてください。

1. **覆しにくい** — 後から考えを変えるコストが無視できない
2. **背景なしでは意外に映る** — 将来の読み手が「なぜこのやり方を選んだのか？」と疑問に思う
3. **本物のトレードオフの結果である** — 実在する選択肢の中から、明確な理由で一つを選んでいる

三つのどれかが欠けていればADRは見送ります。フォーマットは [ADR-FORMAT.md](./ADR-FORMAT.md) を参照してください。
