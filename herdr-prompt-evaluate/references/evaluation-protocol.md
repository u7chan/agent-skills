# 評価プロトコル

## 1. 評価対象を限定する

指示に従って必要な行動・成果が再現されるかを評価する。美しさ、文章の好み、創造性など成果物の主観的品質と、スキルが適切に自動起動するかというトリガー最適化は対象外にする。

対象プロンプトの要求を変えず、曖昧な表現、欠けた境界、暗黙の既定値、競合する指示、検証不能な完了条件を改善対象にする。

## 2. skillの対象範囲を照合する

対象がskillならbaseline前にfrontmatterの`description`が本文の対象範囲を過不足なく表すか照合する。本文にある用途がdescriptionにない、または本文に根拠のない用途をdescriptionが約束する場合だけ、用途の表現を最小修正する。新しい用途、責務、成果物、実行主体が必要なら責務変更として停止する。検索語の追加や自動起動率の調整は行わない。

## 3. シナリオと非公開チェックリストを固定する

評価開始時に次を固定し、反復中に追加・削除・言い換えをしない。

- 標準シナリオ1件: 主要用途を最小の通常条件で通す。
- エッジシナリオ1〜2件: 境界、欠損入力、競合、安全な停止のいずれかを分担する。
- hold-out 1件: baselineと同じ能力を別条件で問う。baseline収束まで実行も内容参照も行わない。

各シナリオへ3〜7件の要件チェック項目を作る。少なくとも1件をcriticalにし、各項目へ観測可能な完全達成条件、部分達成条件、検査対象（pane出力、ファイル、差分、コマンド結果など）を付ける。複数の要求を1項目へ束ねない。

チェックリスト、重要度、期待値、採点基準、hold-out内容、改善仮説を実行Agentの入力、snapshot、worktreeへ置かない。シナリオには実際の利用者が持つ入力と実行に必要な事実だけを書く。

## 4. 観測値を記録する

シナリオごと・イテレーションごとに次を記録する。

| 項目 | 定義 |
| --- | --- |
| requirement_scores | 各要件を完全達成`1`、部分達成`0.5`、未達`0`で記録した一覧 |
| total | 全チェック項目数 |
| accuracy | `100 * sum(requirement_scores) / total`。小数第1位まで保持する |
| critical | critical項目ごとのpass/fail。`1`だけをpassとし、`0.5`と`0`はfailにする |
| success | `herdr agent wait`、回収、採点が成功し、全criticalが`1`ならtrue |
| ambiguities | 実行から新たに観測した、プロンプトだけでは一意に決められない判断点の重複除外一覧 |
| discretion | 指示にないため実行Agentが裁量で補完した判断の重複除外一覧 |
| steps | タスク開始後の観測可能なAgent行動数。ツール呼出し、コマンド実行、ファイル変更、明示的判断を各1とし、待機・画面描画・親の操作は数えない |
| duration | 送信後にworkingを確認してから完了状態を確認するまでの実時間 |
| retries | 再試行回数と各理由。再実行したツール、コマンド、修正を数える |

完全達成の証拠が一部欠けるが要件の一部を観測できる場合だけ`0.5`とし、証拠も達成も確認できなければ`0`にする。同じ不明瞭点や裁量補完の言い換えは1件に正規化する。実行Agentが選択しただけでは曖昧さとせず、複数の適法な選択肢があり結果や副作用が変わるのに選択規則がない場合だけ数える。Agent報告のsteps概数とretriesは回収出力・成果物で照合し、差異があれば親の観測値と根拠を採用する。

## 5. 改善テーマを選ぶ

baseline全体でcritical失敗を最優先し、次に複数シナリオへ波及する曖昧さ、精度低下、steps変動の順で候補を並べる。1回につき1つの根本的な不明瞭点だけをテーマにする。同じ根から生じる近接箇所は1テーマとして最小修正してよい。

指示の追記・置換だけで要求を変えずに直せる場合だけ修正する。新しい機能、責務の移動、入出力契約の変更、章構成の全面変更が必要なら停止する。主観的な成果品質を上げる修正やトリガー文言の最適化を混ぜない。

各回について、テーマ、根拠となる観測、変更箇所、変更量、他テーマを含めなかったことを記録する。

## 6. 収束を計算する

イテレーション2回目以降、各baselineシナリオを直前回の同一シナリオと比較する。

- 全criticalがpassである。
- その回で新たに観測されたambiguitiesが0件である。
- `abs(今回accuracy - 前回accuracy) <= 3.0` ポイントである。
- 前回stepsが0でない場合、`abs(今回steps - 前回steps) / 前回steps <= 0.10` である。両方0なら合格し、片方だけ0なら不合格にする。

全baselineシナリオが同じ回に4条件を満たした時だけ、その回を安定回とする。安定回を2回連続で得た時にbaseline収束とする。途中で1条件でも外れたら連続数を0へ戻す。durationは比較しない。

全baselineシナリオで重複除外したambiguities総数が、直前回より減らない状態が3回連続したら停止する。最大イテレーション数に達した回は採点してから、収束していなければ上限到達として停止する。

## 7. hold-outを判定する

baseline収束後、固定済みhold-outを新しいworktree、workspace、Agentで1回だけ実行する。hold-outの全criticalがpassし、次を満たせば合格にする。

`hold-out accuracy >= 直近2安定回の全baseline accuracyの算術平均 - 15.0`

hold-outの実行前に内容を見て対象プロンプトを修正しない。失敗後もhold-outへ合わせて修正せず、結果と不足を報告して停止する。

## 8. イテレーション結果を提示する

各イテレーションの採点直後に次を提示する。初回の変更点は`なし（baseline）`、停止時の次の修正は停止理由または必要な判断に置き換える。

- その回で評価した変更点。
- シナリオ別のsuccess、accuracy、steps、duration、retriesと理由。
- 新規不明瞭点と新規裁量補完。
- 次の修正として選ぶ1テーマと根拠。
- 現在の連続クリア回数。

## 9. 結果を区別する

- `converged`: baselineが連続2安定回を満たし、hold-outも合格した。
- `stopped`: 実行済み結果はあるが停止条件またはhold-out不合格になった。
- `skipped`: 独立実行を開始できず、実証結果がない。指定文言を表示する。

収束していない状態を「改善済み」や「合格」と表現しない。
