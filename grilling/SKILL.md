# Grilling

計画、意思決定、アイデアの各分岐を徹底的に検討し、依存する判断を上流から一つずつ解決して共通理解へ到達する。

## ルール

- 質問は一度に一つだけ行い、ユーザーの回答を待ってから次へ進む。
- 各質問に具体的な選択肢、推奨回答、簡潔な推奨理由を添える。
- 推奨する選択肢の末尾には必ず `(推奨💡)` を付ける。
- 複数の判断が依存する場合は、下流を決める前に上流の判断を解決する。
- ファイル、コード、ツール、会話から確認できる事実はユーザーに尋ねず、自分で調査する。
- 事実と意思決定を分ける。意思決定は推奨を示したうえで必ずユーザーに委ねる。
- 回答を受けるたびに、決定済み事項、未解決事項、矛盾、次に掘るべき分岐を更新する。
- 共通理解へ到達したとユーザーが確認するまで、実装や外部への反映に移らない。

## 質問フォーマット

次の形式を維持し、質問、選択肢、推奨理由を一行へ詰め込まない。選択肢は `1.` から始まる数字項番だけを使う。

```md
質問{No}: <質問文>

選択肢:
  1. <選択肢A> (推奨💡)
  2. <選択肢B>
  3. <選択肢C>

推奨理由:
  <推奨する理由>
```

選択肢で前提を狭められない場合も、確認できている事実から具体案を作って提示する。必要な選択肢だけを残し、数合わせの案は追加しない。

## 進め方

1. 対象、目的、成功条件、既知の前提を会話と環境から把握する。
2. 判断の依存関係を整理し、最上流の未解決事項を選ぶ。
3. 質問フォーマットに従って一問だけ提示し、回答を待つ。
4. 回答を反映して分岐を再評価し、重要な未解決事項がなくなるまで繰り返す。
5. 決定事項、前提、残る不確実性を要約し、共通理解へ到達したか一問で確認する。
6. 確認後は合意内容を返して終了する。実行が必要なら別の明示的な依頼を待つ。

## 責務境界

- 一般的な計画、キャリア、業務判断、プロダクト案なども対象にする。
- 実装可能な受け入れ条件や移行・運用まで含む設計プランの完成は `design-plan-grill` に任せる。
- 既存文書を根拠にした体系的な設計照合は `design-plan-grill` の docs-backed モードに任せる。
